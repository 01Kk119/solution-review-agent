# 全局汇总规则

## 1. 风险去重

使用以下键判断同一风险：

```text
业务对象 + 失效模式 + 主要证据集合
```

合并时保留一个主风险 ID，选择最贴近根因的主领域，把其他 Agent 写入次生影响或移交，并合并证据和建议，不重复计数。

## 2. 冲突处理

必须披露同一事实的不同数值、严重度差异、建议之间的依赖或互斥、项目原文与口头信息差异，以及版本边界或估算依据冲突。不得静默选值。

可信度说明顺序：

1. 系统约束；
2. 当前用户明确输入；
3. 项目书面原文；
4. 当前附件；
5. 会议口头信息；
6. AI 推断；
7. 领域知识。

该顺序只用于说明可信度，不用于删除冲突。

## 3. 整体风险等级

- `高`：可能阻断安全、合规、核心可行性或合同验收，且无已确认关闭方案。
- `中`：存在重要技术或集成风险，需要验证、补充资料或跨团队关闭。
- `低`：当前证据显示风险可控，关闭条件和责任人明确。

信息不全时必须按潜在影响给出高/中/低暂定等级并降低置信度，同时进入现场适配待确认清单；不得仅因信息不全写“待评估”。`条件性推断` 不提高当前等级。

## 4. 关键风险表

固定表头：

```markdown
| ID | 风险 | 风险等级 | 依据类型 | 影响 | 证据/出处 | 建议动作 | 负责人 |
```

按严重度、是否阻断决策、关闭里程碑、风险 ID 排序。

## 5. 领域归属

- `NAV-*`：导航/定位/控制。
- `DIS-*`：调度/节拍/效率。
- `SW-*`：软件/RCS/接口/HMI。
- `PAP-*`：取放、载具与取放容差。
- `MM-*`：明眸/环境监控系统。
- `GLB-*`：跨域且无法合理归入单一根因的全局风险。

同一风险只在关键风险表出现一次，各领域章节引用该 ID。

## 6. 版本建议规则

- 推荐版本必须同时引用项目需求证据和版本能力基线证据。
- 按单车、RCS/中控、明眸等系统分别展示版本类型、出厂版本、到场目标版本、推荐动作、能力理由、验证和回退。
- `baseline_status=missing` 时，各适用系统版本固定为“待版本负责人确认”。
- 展示替代方案、适配差距、升级/兼容影响、假设和审批状态。
- 版本建议是技术决策建议，不是发布或合同承诺。

## 7. 评审范围边界

- 只评审非标准功能开发风险。
- 硬件选型、EHS、安全认证、土建、施工和一般现场整改统一作为范围外，不形成风险结论、开发项或人时。
- 取放项必须核对载具/货物的名义尺寸、容差、关键几何、停靠偏差和取放能力基线；关键容差缺失时只能待确认。
- 现场适配待确认清单只记录影响能力满足度或新功能判断的缺失条件；每项必须引用关联风险及其暂定等级，不生成现场解决方案。

## 8. 定制化开发附件规则

《定制化开发清单》从 `NonstandardResult.items` 筛选并分三组展示：

- A. 已确认定制开发：`custom_development` 和 `nonstandard_development`；
- B. 版本依赖配置：`version_dependent_configuration`；
- C. 标准能力：`standard_capability` 和 `standard_configuration`。

范围外项不得进入附件。每项沿用稳定 `DEL-*` ID，并带需求/风险/证据引用、实现方式、交付物、验收标准、依赖和责任角色。不得设置或模拟“定制范围 TPM”。

## 9. 非标判定规则

《非标判定清单》是交付项分类结果的严格子集：

- 只有 `classification=nonstandard_development` 的项目进入主表；
- `pending_confirmation` 进入“待判定项”，不能混入已确认非标；
- 每项必须写出推荐版本的标准边界、超出原因、版本策略、验收标准和审批人；
- 缺少权威版本基线时不能确认非标。

## 10. 人时规则

- 单位统一为人时，并注明 `8 人时 = 1 人日`。
- 每个工作项必须引用 `DEL-*`，并按阶段、角色给出低/最可能/高三点区间。
- 每项必须有估算依据、假设、排除项和置信度。
- 客户工作和等待时间默认不计 VisionNav 人时；如需计入必须单列说明。
- 共享设计、联调或测试工作只计一次，避免跨项重复。
- 不可估项单列；不得用 0 替代。
- 总计只汇总已估算项，并明确“不含不可估项”。
- 推荐人时需 TPM 与研发负责人审批后才能成为计划承诺。

## 11. 跨文档一致性

- 版本差距应能追溯到定制清单或明确标为无需动作。
- 所有已确认非标项必须引用一个 `DEL-*` 分类项。
- 所有人时项必须引用一个 `DEL-*`。
- 文档之间的 ID、名称、状态和证据引用必须一致。
- 同一工作项不能在定制、非标和人时文档中使用不同责任模块。
- Markdown 与 HTML 的 ID、结论、版本和人时数字必须一致。

## 12. HTML 呈现规则

- 使用 `assets/html_output_shell.html`，保持示例中的深蓝灰标题区、白色卡片、清晰表格、状态标签和打印样式；
- 页面宽度适合电脑全屏阅读，正文最大宽度约 1180px；
- 复杂表格允许横向滚动，不压缩到不可读；
- 每份附件独立成页，不把四份附件塞入主报告；
- 不依赖外部 CDN、脚本、字体或网络资源，确保本地双击可打开。

## 13. 输出透明度

五份文档都必须说明：

- 已执行和未执行的 Agent；
- 失败或资料缺失造成的覆盖缺口；
- 冲突和待确认条件；
- 建议结论的审批状态。

不要输出 Agent 的隐藏推理过程、完整工具日志或敏感原始附件内容。
