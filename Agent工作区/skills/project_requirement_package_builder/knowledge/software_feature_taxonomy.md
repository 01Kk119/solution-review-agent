# 软件需求识别知识（software_feature_taxonomy）

> 用途：把资料中的软件类需求归类，并标出“疑似非标”的信号。
> 硬约束：**只能写“资料显示可能涉及非标，需 TPM 判断”，不能下最终非标结论。**

## 软件需求归类

| 类别 | 典型内容 |
|---|---|
| 调度逻辑 | 任务分派、优先级、多车协同、区域互斥、交管 |
| 策略类 | 峰值补差策略、库位分配策略、充电策略、就近派单 |
| 接口集成 | PLC/WMS/WCS/MES/扫码枪/输送线/门/电梯/监控 |
| 车端行为 | 停车-鸣笛-等待类现场规则、灯光逻辑、速度分区 |
| HMI/交互 | 平板操作、呼叫按钮、状态看板、库存状态人工更新 |
| 库存管理 | 线库库位管理、先进先出、只放不取边界 |
| 数据/报表 | 效率统计、任务追溯、监控联动 |

## 疑似非标信号清单

出现以下情况时，在 7.4 节登记为“可能非标项”，字段：需求描述 / 来源 /
是否明确 / 是否需 TPM 判断 / 可能影响模块：

1. **客户点名复刻竞品/既有系统行为**（“像 XX 系统那样…”）
2. **现场自定义交通规则**（特定点停车 N 秒、鸣笛、灯光频闪规则）
3. **人工输入驱动的策略切换**（班前输入产量 → 激活某流程）
4. **非标准接口协议**或客户自有信号体系（PLC 自定义报文）
5. **库存管理边界特殊**（我方只管放、客户平板改状态等混合管理）
6. **特殊区域逻辑**（次品区、hospital 类特殊存储区的专属规则）
7. **报警/监控联动**（摄像头系统与调度联动）
8. **版本约束**（指定 IGV 大版本、指定 RCS/VFS 架构、与老项目共存）

## 登记注意

- 每条注明**是标准能力内还是待判断**——判断不了就写“需 TPM 判断”。
- 口头需求（转写来源）单独标注，提示方案落纸确认。
- 客户方文档里的合同性表述（“shall…”）逐条保留原文要点，不得弱化。
