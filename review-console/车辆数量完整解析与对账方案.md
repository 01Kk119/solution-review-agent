# 车辆数量轻量解析与对账方案

## 1. 目标

用最少步骤解决“漏页、错加、口径混用”：

```text
本地快速索引（0 Token）
→ 数量候选提取（0 Token）
→ 程序对账（0 Token）
→ 仅歧义项调用模型（通常0～800 Token）
```

设计目标：

- 普通项目处理时间控制在秒级。
- 绝大多数项目不调用模型。
- 不把PPT、Excel全文放入模型上下文。
- 文件无论多长都不得静默截断。
- 总数由程序计算，模型只解释歧义。

## 2. 最小处理流程

### 2.1 本地快速索引

直接读取Office压缩包中的XML，不渲染页面：

- PPTX：读取所有 `slide*.xml`，记录总页数和每页文字。
- XLSX：读取Sheet名称、单元格值、公式和表格范围。
- DOCX：读取正文与表格。
- PDF：优先读取文本层。

默认不做：

- 不渲染全部PPT页面。
- 不生成全文Markdown副本。
- 不提取无关图片。
- 不对有文本层的页面做OCR。
- 不把全文发给模型。

仅保存一个紧凑索引：

```json
{
  "file": "proposal.pptx",
  "total_units": 134,
  "indexed_units": 134,
  "complete": true,
  "hits": []
}
```

硬门禁：

```text
indexed_units != total_units
→ 禁止输出确定车辆总数
```

### 2.2 数量候选提取

本地规则只扫描车辆相关内容：

```text
AGV | AMR | vehicle | forklift | VNE | VNP | 车辆
Qty | Quantity | Total | units | 台 | required
existing | current | new | expansion | simulation | spare
```

命中后只保留：

- 当前页/表格
- Zone或项目名称
- 车型
- 数字
- 数量口径关键词
- 文件和页码/Sheet

不保留大段上下文。单条证据建议控制在300字符以内。

### 2.3 程序对账

统一成最小数据结构：

```json
{
  "scope": "Zone 22",
  "model": "VNE40",
  "quantity": 21,
  "kind": "required",
  "source": "F01#slide94",
  "authority": 3
}
```

`kind`只允许：

- `project_total`
- `existing`
- `new`
- `required`
- `simulation`
- `spare`
- `unknown`

权威优先级：

```text
人工确认/正式车辆清单
> 项目总表
> 分区表格Total
> 页面Conclusion
> 仿真数量
```

程序执行：

1. 按 `scope + model + kind` 去重。
2. 只累加口径一致的记录。
3. 低权威记录不能覆盖高权威记录。
4. 项目总数与分区小计分别保存，不强行混成一个数字。
5. 结果由代码求和，模型不得改写。

本项目记录示例：

```json
{
  "authoritative_total": 98,
  "expression": "89+9",
  "status": "PASS_WITH_NOTE",
  "note": "车型、Zone及现有/新增拆分待正式清单展开"
}
```

## 3. 只保留四个冲突检查

为保证速度，不做复杂推理，只检查最高价值的四类错误：

1. 解析覆盖率不足100%。
2. 同一范围的Conclusion与表格Total不一致。
3. 项目总数与分区小计不一致。
4. 同一数量可能同时属于现有和新增。

状态只有三种：

- `PASS`：总数和明细闭环。
- `PASS_WITH_NOTE`：有权威总数，但拆分不完整。
- `BLOCKED`：没有可靠总数或存在未解决冲突。

最终报告必须直接读取该状态和程序结果。

## 4. 模型调用策略

### 4.1 默认不调用

满足以下条件时，模型调用为0：

- 文件索引完整。
- 找到正式总数或项目总表。
- 数量口径明确。
- 没有冲突。

### 4.2 仅发送歧义项

只有 `kind=unknown` 或存在冲突时才调用模型。输入示例：

```text
任务：判断以下两条数量的口径，不要计算总数。
1. Zone 24，Conclusion=5台，slide115
2. Zone 24，Table Total=6台，slide115
输出：冲突类型、推荐采用项、需确认问题。
```

模型只输出结构化JSON：

```json
{
  "classification": "conflict",
  "recommended_record": null,
  "question": "请确认Zone 24最终配置为5台还是6台"
}
```

禁止模型：

- 阅读完整附件。
- 自行重新求和。
- 补造缺失数据。
- 覆盖程序计算结果。

## 5. Token与速度预算

| 场景 | 模型输入 | 预计Token |
|---|---:|---:|
| 数量清晰、无冲突 | 0字符 | 0 |
| 1～3个歧义 | 500～1,500字符 | 约200～600 |
| 多Zone且有少量冲突 | 不超过2,400字符 | 不超过800 |
| 超过预算 | 分批或转人工 | 不继续扩大上下文 |

性能目标：

- Office XML索引：通常1～3秒。
- 关键词提取与求和：通常低于1秒。
- 无歧义项目：全流程不调用模型。
- 禁止通过提高上下文上限解决漏页。

## 6. 最少输出文件

每次评审只新增一个结构化文件：

```text
vehicle_reconciliation.json
```

内容包括：

```json
{
  "coverage": {
    "complete": true,
    "files": ["F01:134/134", "F02:42/42", "F03:全部Sheet"]
  },
  "records": [],
  "authoritative_total": 98,
  "calculated_subtotal": null,
  "conflicts": [],
  "status": "PASS_WITH_NOTE"
}
```

不再默认生成：

- 全文解析Markdown
- 多份候选JSON
- 单独的数量台账Markdown
- 重复的中间摘要

调试时才临时输出详细索引。

## 7. 对现有代码的最小改造

不拆分大量新模块，先在现有程序中增加三个函数：

```python
index_source_units(path)
extract_vehicle_records(index)
reconcile_vehicle_records(records, confirmed_total=None)
```

修改点：

1. `load_project_context()`继续服务模型摘要，但不得承担事实完整性解析。
2. 评审开始时先运行本地索引和数量对账。
3. 将对账结果控制在约2,400字符内，再放入模型提示词。
4. 最终报告中的车辆总数只能读取 `vehicle_reconciliation.json`。
5. 有 `BLOCKED` 状态时，报告只能写“待确认”，不能输出确定总数。

## 8. 最小测试集

只保留六个关键测试：

1. 134页PPT必须显示134/134。
2. 数字位于最后一页时仍能提取。
3. 三个附件不能因字符预算截断。
4. Conclusion=5、Table Total=6时必须报警。
5. 正式总数98、分区小计不足时输出98并标记拆分未闭环。
6. 模型返回的数字与程序结果不一致时，必须采用程序结果。

## 9. 实施顺序

### P0：半天至一天

- 完成逐页/逐Sheet索引。
- 增加100%覆盖率门禁。
- 增加人工确认总数字段。
- 最终报告改读结构化总数。

### P1：一天

- 增加数量候选规则。
- 实现去重、求和和四类冲突检查。
- 生成单一 `vehicle_reconciliation.json`。

### P2：半天

- 仅对歧义项调用模型。
- 增加800 Token硬预算和结果缓存。

预期总改造量约2～3个工作日；P0完成后即可先阻止本次类型的严重漏算。
