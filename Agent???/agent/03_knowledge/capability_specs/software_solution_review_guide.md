# 软件方案评审指导：软件影响分析、版本匹配与非标开发识别

## 1. 使用目的

本指导供软件 TPM 在机器人项目方案评审中使用，核心目标是：

1. 从客户需求、机电结构变化和现场作业流程中识别软件影响。
2. 判断需求是否已被目标软件版本覆盖。
3. 区分标准配置、版本依赖、适配工作和疑似非标开发。
4. 明确需要研发确认的接口、模块、测试和交付风险。
5. 输出有证据、可追溯、可关闭的软件评审结论。

本指导不能代替研发立项结论。资料不足时，只能标记为“待确认”或“疑似非标”，不得自行认定已经支持，也不得自行认定必须开发。

## 2. 适用范围与版本边界

本指导纳入以下版本能力：

- 5.2.2：仅采用发布说明中明确标记为 `250930` 的条目。
- 5.3.2：采用 `260430` 主版本的规划特性和增补特性。

### 2.1 强制版本对比顺序

除非客户合同或项目基线明确指定其他版本，软件评审必须按以下顺序执行：

1. 先只使用 5.2.2／250930 能力基线逐项匹配客户需求；
2. 若 5.2.2 有明确能力证据且适用条件一致，停止向上比较，按 5.2.2 评估；
3. 只有出现“5.2.2 明确不支持、适用条件不满足、能力边界不足或无对应能力证据”之一时，才加载并对比 5.3.2／260430；
4. 进入 5.3.2 分析时，必须写明触发上探的具体需求、5.2.2 差距及 5.3.2 对应能力证据；
5. 5.3.2 仍无法证明覆盖时，登记为待确认或疑似非标开发风险，不得因为版本更新而默认满足。

禁止默认同时铺开两个版本进行宽泛比较，也禁止仅因 5.3.2 更新就直接推荐新版本。

发布说明中标记为其他版本的条目不作为本指导的能力依据。不能因为某项能力出现在同一份发布说明中，就默认它属于当前评审版本。

版本能力只能说明“发布说明记录了该能力”，不能自动证明：

- 已适配项目所选车型和控制器；
- 已覆盖客户现场的货物、载具和工况；
- 已通过当前项目要求的性能、稳定性或安全验证；
- 能与项目所选 RCS、VFS、WMS、WCS、PLC 或第三方设备直接兼容；
- 不需要参数配置、二次验证或现场联调。

## 3. 软件评审的基本原则

### 3.1 先判断影响，再判断是否非标

评审顺序必须是：

```text
需求或硬件变化
→ 外部行为、信号、数据或流程是否变化
→ 影响哪些软件层
→ 目标版本是否存在对应能力
→ 车型、硬件、协议和场景是否满足适用条件
→ 配置、适配、开发或待确认
```

硬件变化本身不等于软件非标。只有当变化导致现有软件的输入、输出、状态、控制、接口、流程或安全逻辑超出现有能力边界时，才可能产生适配或非标开发。

### 3.2 结论必须有证据

每项结论至少关联一种证据：

- 客户需求、技术协议或现场调研记录；
- 车型、硬件 BOM、电气图、IO 点表或通信协议；
- 软件发布说明中的具体版本条目；
- 标准能力规格；
- 研发、测试或产品经理的书面确认；
- 已验证项目或测试报告。

口头说明只能记录为待落纸证据，不能单独作为“标准支持”结论。

### 3.3 不把“有功能”当成“项目可直接使用”

版本中存在同名功能时，仍需核对：

- 适用车型；
- 控制器或板卡；
- 传感器及安装方式；
- 载具、货物和库位特征；
- RCS、车端、工具和协议版本；
- 参数和数据格式；
- 正常、异常及恢复流程；
- 性能、安全和验收指标。

## 4. 软件影响分析方法

## 4.1 第一步：识别变化源

逐项登记项目相对标准产品的变化。

| 变化源 | 需要确认的内容 |
|---|---|
| 机械结构 | 车体尺寸、轴距、轮距、门架、货叉、属具、转向结构、举升和横移机构 |
| 电气硬件 | 控制器、DCU、驱动器、编码器、传感器、按钮、灯光、音箱、IO |
| 感知硬件 | 激光雷达、相机、RGBD、叉端雷达、安装位置、视场和遮挡 |
| 车型 | P、E、Q、ST、R、SL、L 等具体车型及变体 |
| 货物与载具 | 托盘、料笼、卡板箱、缠膜、插环、尺寸、重量、堆叠方式 |
| 场景 | 货架、线库、装卸车、堆叠、拆垛、动态搜索、长路径、大地图 |
| 外部系统 | WMS、WCS、MES、ERP、PLC、输送线、门、电梯、明眸 |
| 用户操作 | Robotune、HMI、任务创建、异常处理、维保、数据导入导出 |
| 项目规则 | 优先级、交通管制、停车鸣笛、灯光、充电、库存和异常流转 |

## 4.2 第二步：判断软件可观察到的变化

如果变化影响下列任一对象，就进入软件影响分析：

- 新增或改变输入信号；
- 新增或改变控制输出；
- 新增传感器数据或数据格式；
- 新增设备状态、故障码或报警；
- 改变车辆运动学、速度、转向或停车行为；
- 改变取放货状态机；
- 改变安全互锁或降级策略；
- 改变任务流程、调度规则或库存状态；
- 改变外部接口、字段、握手时序或通信频率；
- 改变工具页面、参数、权限、日志或数据导入导出；
- 改变版本兼容关系或部署方式。

如果以上均不变化，并且现有参数范围可以覆盖，可暂定为“无软件开发影响”，但仍需记录参数调整和验证工作。

## 4.3 第三步：按软件层拆解影响

| 软件层 | 主要评审对象 | 典型影响 |
|---|---|---|
| 感知 | 托盘、货物、障碍物、插环、缠膜、空间检测 | 模型、点云、图像、检测接口、置信度、误检漏检 |
| 定位与导航 | 地图、重定位、里程计、雷达、路径 | 地图格式、标定、定位精度、长路径、大地图 |
| 控制 | 行驶、转向、停车、速度规划、伺服 | 运动学参数、控制模式、精度、稳定性 |
| 车端固件 | IO、属具、状态机、互锁、故障 | 信号映射、动作流程、超时、异常恢复 |
| RCS/VFS | 任务、路径、交通管制、资源和状态 | 调度策略、任务字段、流程编排、降级处理 |
| 接口集成 | WMS/WCS/MES/PLC/VDA5050 | 协议、字段、时序、重试、幂等、状态回滚 |
| 工具 | Robotune、AgvHub、标定软件、MPE | 参数、页面、校验、日志、导入导出 |
| 运维 | 维保、日志、授权、部署和升级 | 计数、告警、诊断、兼容矩阵、回滚 |
| 明眸 | 库位监控、单车联动和Web系统 | 识别、通信延迟、断线、隐私和安全联动 |

## 4.4 第四步：重建完整业务流程

不能只检查单个动作。至少按以下链路评审：

```text
任务来源
→ 任务创建与校验
→ RCS/VFS分派
→ 路径与交通管制
→ 车辆到位
→ 感知检测
→ 固件/控制执行
→ 动作结果确认
→ 状态回传
→ 外部系统更新
→ 异常、重试、人工介入和恢复
```

对每个环节确认：

- 谁发起；
- 输入是什么；
- 输出是什么；
- 成功条件是什么；
- 失败如何识别；
- 是否重试；
- 是否允许人工接管；
- 恢复后状态如何对齐；
- 哪个系统保存最终状态。

## 4.5 第五步：匹配目标版本

先匹配 5.2.2；只有 5.2.2 无法满足时才继续匹配 5.3.2。不得颠倒顺序或跳过 5.2.2 基线。

版本匹配必须同时满足：

1. 发布说明存在对应能力。
2. 条目标记属于目标版本。
3. 项目车型在适用范围内。
4. 硬件、传感器、板卡和属具满足条件。
5. 场景、货物、载具和动作流程一致。
6. 车端、RCS、工具及外部接口版本兼容。
7. 验收指标没有超出已验证边界。

任何一项不明确，都不能直接判定为标准覆盖。

## 5. 非标开发判定方法

## 5.1 结论分类

| 分类 | 判定标准 | 是否计入非标开发 |
|---|---|---|
| 标准能力直接覆盖 | 目标版本、车型、硬件和场景均有明确证据 | 否 |
| 标准配置 | 只需在既有参数、地图、规则或页面中配置 | 否，但登记实施和测试工作 |
| 版本依赖 | 标准能力存在，但当前项目基线版本不具备或兼容性未确认 | 暂不判非标，先做版本决策 |
| 标准适配 | 已有框架或驱动，需要做点表、字段、参数或设备适配 | 是否非标由组织口径确认 |
| 疑似非标 | 需要新增算法、状态机、接口、页面、控制逻辑或异常流程 | 是候选项，需研发评估 |
| 待确认 | 资料不足，无法判断 | 不得擅自归类 |

## 5.2 疑似非标触发条件

出现以下任一情况，应登记为疑似非标开发项：

- 目标版本没有对应能力。
- 客户要求的车型或硬件不在已验证范围内。
- 新增传感器、执行机构或属具，现有软件无对应驱动和控制流程。
- 改变车端动作状态机、安全互锁、超时或异常恢复。
- 客户要求私有协议、特殊字段或非标准握手时序。
- 新增RCS调度策略、资源模型、库存规则或特殊业务流程。
- 新增Robotune、HMI、看板、报表或权限能力。
- 要求新的感知对象、识别模型或特殊安装方式。
- 要求超出版本说明或测试证据的精度、节拍、规模或稳定性。
- 需要修改标准接口的数据结构或破坏现有兼容性。
- 需要为单项目维护独立代码分支。

## 5.3 不应直接判为非标的情况

- 标准参数范围内的调参。
- 标准地图、点位、区域和交通规则配置。
- 已有标准接口范围内的字段映射和联调。
- 已有工具支持的数据导入、导出和校验。
- 版本已明确支持、适用条件一致的标准功能启用。

以上工作即使不计非标，也必须估算实施、配置、验证和联调工作量。

## 6. 5.2.2／250930软件能力基线

以下仅收录原发布说明中明确标记为 `250930` 的软件相关能力。

## 6.1 Linux与运行环境

- Docker CPU分配。
- 支持配置关闭息屏。
- 用户名切换为`agv`，涉及日志写入目录和安装脚本目录权限。
- 桌面快捷启动方式。
- 中文输入法安装。
- 虚拟软键盘。

评审用途：

- 确认项目是否修改Linux用户、目录、权限、容器资源或部署方式。
- 若客户安全策略、IT策略或定制镜像要求改变上述机制，需评估部署脚本、权限和日志链路是否需要适配。

## 6.2 Robotune与标定工具

- Robotune日志打包。
- Robotune增加新参数调试界面。
- Robotune支持动态载具。
- Robotune本机清除控制权。
- 标定软件增加初始值设置。

评审用途：

- 判断项目参数能否通过既有界面配置。
- 核对动态载具的数据结构和项目载具类型是否一致。
- 明确控制权清除、权限和误操作防护。
- 若需要新增页面、参数类型、批量操作或校验规则，登记为疑似非标。

## 6.3 导航、定位与地图工具

- 各车型支持手持器地图导航，包含重定位优化。
- 拓展建图功能支持手持器地图。
- 支持10万平方米手持器地图。
- P、E车型支持里程计高精对时同步。
- 里程计同步精度估计工具。
- MPE地图一键优化加入自动回环。
- MPE地图质量评估，包括墙厚、局部一致性和建图位姿海拔热力图。
- Linux下支持墙角多雷达标定。
- 现场多车一致性校验方法。
- 导航漂移报警，由控制检测并报错。
- 立体防护的减速区域优化。
- 立体防护的取放货库位优化。

评审用途：

- 大地图需求必须确认面积、车辆数量、地图数据量和性能指标。
- 里程计高精对时的明确车型只有P、E；其他车型不得直接套用。
- 新雷达型号、新安装位置或非墙角标定条件需重新确认。
- 若客户要求新的地图格式、质量指标、报警策略或定位降级流程，需判断是否产生适配或非标。

## 6.4 感知、取放货与控制

- E车大料笼通用堆叠闭环、堆叠确认、出叉安全校验。
- E车抱闸提升底盘末端取放精度，发布说明记录为3 mm。
- 伺服堆叠时空间安全防护。
- R车横梁式、穿梭式货架伺服闭环。
- 货架实时障碍物路径规划。
- 自动二次取货。
- 放货出叉位姿校验。
- 根据任务特性参数执行二阶段取放货。
- 电动升降机制优化。
- R车后向安全。
- ST伺服卸车及卸车实时障碍物路径规划。
- 机械臂站台反光板伺服及控制自适应优化。
- 板货二次货位放货检测、出叉安全检测和高度自适应堆拆垛。
- 窄墩托盘、模糊缠膜和网面托盘检测。
- DT35取货防推。
- 精准入叉防撞。
- 放货控制自适应空间优化。
- 伺服路径规划算法优化。
- 伺服横移。
- 新水平与垂直到位逻辑。
- 货物状态保持逻辑优化。
- 明眸安全功能。

评审用途：

- 名称相似不代表场景相同，必须比对车型、货物、载具、库位、传感器和流程。
- 对精度、节拍、防撞、安全校验等指标，必须取得测试或验收依据。
- 客户要求改变二阶段取放、到位判断、堆叠确认或降级流程时，应重点检查车端状态机和RCS任务流程。

## 6.5 库位明眸

- 前后端分离的Web化明眸系统。
- 明眸与单车直联的低延迟安全联动机制。
- 自动标注工具。
- 隐私保护。
- 断线提示。
- 断线重新连接。

评审用途：

- 确认相机、服务器、网络、覆盖区域和单车连接方式。
- 明确断线时车辆动作、任务状态和安全策略。
- 客户要求新的监控对象、页面、接口或联动规则时，需评估明眸、车端和RCS三方改动。

## 7. 5.3.2／260430软件能力基线

## 7.1 生产与调试工具

- AgvHub通参工具箱在导出JSON前进行数据自我校验。
- Robotune出厂界面语言为英语。
- Robotune通信连接稳定性优化。
- WebSocket性能优化，避免任务状态异常。
- Robotune任务失败提醒优化：
  - 弹窗提示失败原因；
  - 指出配置错误的搬运方案。

评审用途：

- 客户需要其他默认语言时，确认是已有配置还是需要修改出厂逻辑。
- 自定义JSON字段或数据规则需确认现有导出校验是否覆盖。
- 对通信断连，必须确认重连、超时、任务状态、重复下发和状态回滚。
- 若需要新增失败原因、诊断规则或用户提示，登记工具和应用层影响。

## 7.2 维保能力

- 维保任务支持行驶里程计数。
- 维保任务支持电池循环计数。
- 仅适配DCU板车型。
- 已验证E、P、R车型。
- Q、SL、L车型未验证。

评审用途：

- 先确认控制器板型和车型，再判断是否覆盖。
- 未验证车型只能标记为待验证，不能写成标准支持。
- 客户要求新的维保触发条件、计数口径、提醒渠道或报表时，需评估非标。

## 7.3 复杂场景与感知

- E40-07大料笼堆叠半驶离确认。
- E40-07大料笼堆叠失败优雅降级。
- 带智能货叉2.0的料笼堆叠闭环。
- P15-66卡板箱闭环检测。
- P15-66卡板箱横移和前后堆叠策略。
- P15-66缠膜托盘RGBD检测。
- 缠膜托盘自动标注软件。
- 插环检测。
- 多雷达库上报激光异常错误码。
- 智能货叉2.0半入叉两级优先级配置，任务特性参数优先于通过`pallectTypeID`查询的载具库参数。

评审用途：

- 确认项目车型、智能货叉版本、相机类型、料笼和卡板箱特征。
- 新货物外观、缠膜方式、插环形态或传感器安装方式不得直接判定为已覆盖。
- 优雅降级必须说明触发条件、车辆动作、任务状态和人工恢复方式。
- 新错误码需确认车端上报、RCS展示、日志记录和用户处理建议。

## 7.4 导航、定位、控制与算力

- 重定位彩色方案。
- Last pose数据库优化。
- 长路径窗口滚动下发。
- Double S速度规划优化。
- Ver1算法自适应降采样优化。
- MPE抠图效果选择易读。
- Linux分核、优先级和内存优化。
- OpenVINO版本升级适配。
- 增补软件条目记录“分核”，但原文件未提供完整功能说明和适用边界。

评审用途：

- 长路径需求必须确认最长路径、车辆数、下发窗口、断连和任务恢复。
- Double S速度规划是否满足具体加速度、减速度和冲击度指标，需要控制团队确认。
- Last pose、重定位彩色方案和自适应降采样的适用条件需引用专项文档或测试结果。
- OpenVINO升级可能影响模型、接口、算力和部署兼容性，涉及新模型时必须验证。
- “分核”条目信息不完整，只能作为待确认项，不能推断具体性能收益。

## 8. 5.2.2与5.3.2差异评审

| 评审维度 | 5.2.2／250930 | 5.3.2／260430 | 非标判断关注点 |
|---|---|---|---|
| 平台与部署 | Linux环境、Docker CPU、用户和目录权限 | Linux分核、优先级、内存优化 | 客户IT策略、镜像、权限和算力配置是否超出现有机制 |

| 控制 | 伺服效率、横移、到位逻辑和防撞 | 长路径滚动下发、Double S速度规划 | 新运动学、精度、速度曲线或控制状态机 |
| 感知取放 | 料笼、货架、ST卸车、板货、托盘检测 | 半驶离、优雅降级、缠膜RGBD、插环、卡板箱 | 项目对象和已验证对象是否一致 |

| 算力 | 未在本指导中记录专项算力库升级 | OpenVINO升级适配 | 新模型和硬件算力是否兼容 |

版本选择不能只按“新版本功能更多”判断，应结合：

- 项目交付时间和版本发布状态；
- 车型与控制器；
- 场景能力；
- RCS、车端和工具兼容矩阵；
- 已验证项目和测试覆盖；
- 现场升级、回滚及长期维护策略。

## 9. 重点评审问题

### 9.1 车型与硬件

- 项目具体车型、车体变体和控制器板型是什么？
- 是否更换电机、驱动器、编码器、雷达、相机或属具？
- 新硬件是否有标准驱动、错误码和状态上报？
- 运动学、标定、IO和安全互锁是否变化？

### 9.2 感知与取放

- 货物、托盘、料笼和库位是否与版本验证对象一致？
- 是否存在缠膜、反光、黑色、网面、窄墩、插环或遮挡？
- 检测失败后车辆、任务和人工处理流程是什么？
- 精度、节拍、误检率、漏检率和安全距离如何验收？

### 9.3 导航与控制

- 地图面积、最长路径、车辆数量和并发量是多少？
- 使用何种建图、重定位和标定方式？
- 停车精度、速度、加减速度和冲击度要求是什么？
- 定位漂移、通信断开或路径下发失败后如何恢复？

### 9.4 调度与接口

- 采用RCS还是VFS？车端和调度版本如何配套？
- 任务由谁创建，最终状态由谁保存？
- WMS、WCS、MES、PLC使用什么协议和字段？
- 是否需要VDA5050或客户私有协议？
- 是否有重试、幂等、超时、回滚和人工补偿？

### 9.5 工具与运维

- Robotune是否需要新增参数、页面、语言或权限？
- AgvHub的JSON校验是否覆盖项目自定义数据？
- 日志是否能定位通信、感知、控制和任务失败原因？
- 维保计数是否适配项目车型和板卡？
- 如何升级、回滚、备份配置并恢复控制权？

## 11. 评审输出要求

软件方案评审至少输出以下内容：

1. 项目软件架构及版本组合。
2. 车型、硬件、传感器和软件兼容矩阵。
3. 业务流程和系统交互链路。
4. 外部接口清单及协议状态。
5. 目标版本能力匹配表。
6. 标准配置项清单。
7. 版本依赖项清单。
8. 标准适配项清单。
9. 疑似非标开发项清单。
10. 待确认问题及责任人。
11. 测试、验收、升级和回滚要求。

推荐使用以下结论句式：

- “发布说明明确记录该能力，且车型、硬件和场景条件一致，暂按标准能力评估，仍需完成项目验证。”
- “发布说明存在同名能力，但项目适用条件未确认，当前标记为版本依赖／待确认。”
- “现有能力无法证明覆盖客户新增流程，涉及新增状态机／接口／算法，登记为疑似非标开发项。”
- “当前资料未说明该能力，不作支持性判断，提交研发确认。”

## 12. 禁止性规则

- 禁止把不同版本的条目混写成同一版本能力。
- 禁止根据功能名称推测适用车型和场景。
- 禁止把“计划、增补、仅合并、未测试、未验证”写成已稳定交付。
- 禁止在没有接口资料时自行补充字段、协议或时序。
- 禁止在没有测试证据时承诺精度、节拍、规模和稳定性。
- 禁止因使用较新版本就直接判定“不需要非标开发”。
- 禁止把配置、适配、开发和测试工作混为一类。
